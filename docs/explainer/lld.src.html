Settlement Lab

Low-level design in 10 minutes · what it is, how it works, and what it measured
In one sentence: a Java engine that moves money between accounts from many threads at once and proves it never creates, loses or double-posts a single paisa, even when messages arrive twice, the downstream ledger is slow or down, and traffic is higher than it can handle.

Is it just "add and subtract funds"? Yes and no.

The arithmetic is deliberately simple: debit one account, credit another. That part is not the project. A naive version does the arithmetic once, on one thread, with happy inputs. Payment engineering is everything that happens around that one line when real conditions hit it:

Naive version

  • One user, one thread
  • Every message arrives once
  • Every downstream call succeeds
  • "It worked when I tried it"

Settlement Lab

  • Many threads on the same accounts
  • Duplicates injected on purpose
  • Ledger made slow, flaky, or down
  • Correctness proved by invariant tests and measured

The hard questions in payments are not "can you add two numbers" but "what if two threads debit the same account?", "what if the message is delivered twice?", "what if the ledger times out halfway?". This project is a working, tested answer to each of them, with the code and the tests in the open.

Scope. Today everything is in memory, in one process, with no database. That keeps the concurrency rules visible in plain Java. Section 8 shows how the same rules move into PostgreSQL, the planned v3.

1 · The four problems it solves

Problem What goes wrong in a real system How Settlement Lab handles it How it is proved
Race conditions Two threads read balance 100, both debit 80, both succeed: money created from nothing. Each account has its own lock; both accounts are locked before the debit and credit. Stress tests with many threads; total must stay identical.
Deadlock T1 locks A and waits for B, T2 locks B and waits for A: both stuck forever. Always lock the lower account id first. No cycle of waits is possible. Opposing transfers (A→B, B→A) run together under a timeout.
Duplicates A network retry delivers the same payment twice; customer charged twice. Idempotency store: the first copy is processed, every copy gets the same answer. 2 % duplicates injected in every run; "posted twice" must be 0.
Failing downstream The general ledger (GL) is slow or down; threads pile up; the whole system falls over. Answer the caller once the ledger posts; publish to the GL afterwards with retry, a circuit breaker and an outbox. Runs with FLAKY and OUTAGE faults; the GL must end equal to the ledger.

Plus overload: a bounded queue. When it is full the caller is told "busy, retry" (503) instead of the server running out of memory. This is called back-pressure.

The four invariants (rules that must hold after every run)

1 the sum of all balances never changes  ·  2 no transfer is posted twice  ·  3 no balance goes below zero  ·  4 the general ledger holds exactly the ledger's postings

An invariant checker verifies these at the end of every test and every benchmark scenario. This is the heart of the project: not "it seems to work", but "here is the rule, and here is the check that runs it 100,000 times under faults".

Key terms

Ledger The book of account balances and postings. Source of truth.
Posting The record that a transfer was applied (id, accounts, amount, sequence).
General ledger (GL) The downstream accounting system that must receive every posting. Here it is a fake with injectable faults.
Idempotent Doing it twice has the same effect as doing it once.
Outbox A holding area for postings the GL has not accepted yet; resent until they land.
Circuit breaker Stops calling a failing service for a while, so it is not hammered while sick.
Virtual threads Java 21 lightweight threads; cheap to block. Compared against classic platform threads.

2 · Architecture and dependencies

Two Maven modules. The engine never imports Spring; a test (ArchUnit) fails the build if anyone tries. The API is a thin layer on top.

Runtime dependencies (deliberately few)

  • Java 21+ (built for 21, run on 25): locks, atomics, CompletableFuture, virtual threads
  • Resilience4j: retry and circuit breaker
  • Spring Boot 4 (API module only): web, validation

Test and build

  • JUnit 5, AssertJ, jqwik (property tests), Awaitility, ArchUnit
  • Maven wrapper, JaCoCo 85 % gate, Spotless formatter
  • GitHub Actions: Ubuntu + Windows × JDK 21 + 25

Is there a database? No, on purpose.

Accounts live in Java memory. The goal of v1 was to show in-process concurrency (locks, atomics, threads) with nothing hiding it: no database doing the locking for you.

Trade-off: a crash loses state, and it cannot run on two servers. In a real bank, balances and the outbox live in a database with transactions.

Next (v3): a PostgresLedger next to the two in-memory ones, passing the same invariant tests (see section 8).

Two ledger implementations, one interface

LockingLedger (pessimistic) CasLedger (optimistic)
One ReentrantLock per account. Lock both accounts in ascending id order, debit, credit, unlock in finally. No locks. The balance table is an immutable array swapped with compareAndSet; on conflict, copy and retry.
Unrelated transfers run in parallel. Every write copies the whole table; contention causes retries.

Both pass the same tests. The runner measures which is faster and why (section 5), instead of assuming that lock-free must be faster.

3 · One transfer, end to end

The animated version of this diagram (flow.svg) moves transfers through the pipeline; the red one is a duplicate, answered at the idempotency store.
# Step What happens Answer to caller
1 Idempotency store A map of transfer id → future result, claimed with one atomic putIfAbsent. First caller owns it; a duplicate waits for the same future. Duplicate: the original answer
2 Validator Amount above zero, accounts exist and differ. 400 with the reason
3 Bounded queue ArrayBlockingQueue; waits at most 100 ms for space. Full: 503 + Retry-After
4 Worker 8 workers, either platform threads or virtual threads behind a semaphore (fair comparison). –
5 Ledger Lock both accounts (or CAS), check funds, debit and credit atomically, record the posting. 201 posted · 422 no funds
6 Publish to GL Sent on a separate thread, so the caller never waits for the GL. Retry 3× with jitter inside a circuit breaker; failures go to the outbox and are resent. (already answered)

Why answer before the GL confirms?

The ledger is the source of truth. If the caller had to wait for the GL, a GL outage would stop all payments. Instead the GL is eventually consistent: it always catches up, because the outbox never drops a posting and the GL ignores a posting id it already has. At-least-once delivery + an idempotent receiver = an exactly-once effect.

4 · Two ideas worth a closer look

Why ordered locking cannot deadlock. Animated in locking.svg.

The argument, not just the slogan: a deadlock needs a cycle of threads, each holding a lock the next one wants. With one global order, a thread holding lock k only ever waits for a lock higher than k. Going round a cycle, ids would have to keep rising and still come back to the start, which is impossible.

Circuit breaker states around the general ledger. Animated in breaker.svg.

Why the breaker sits outside the retry: when the breaker is open, one publish attempt fails immediately instead of retrying three times against a service that is known to be down. Retry handles blips; the breaker handles outages; the outbox makes sure nothing is lost in either case.

5 · Results: what the numbers say

One committed run: 10,000 accounts, 100,000 transfers per scenario, 20 % of traffic on 20 "hot" accounts, 2 % duplicates, 8 workers, 4-core cloud machine, JDK 21. All 12 scenarios passed every invariant. A selection:

Ledger Threads GL faults Transfers/s p99 µs Duplicates Outbox peak Invariants
Locking Platform None 248,861 2,008 2,006 0 PASS
Locking Virtual Flaky 225,608 735 2,006 3 PASS
Locking Platform Outage 172,734 2,840 2,006 90,036 PASS
CAS Platform None 54,027 9,488 2,006 0 PASS
CAS Virtual None 55,465 3,779 2,006 0 PASS

Findings

  • Ordered locking beat CAS by 2.8× to 4.6×. Each CAS write copies an 80 KB table and throws it away on conflict; locks touch only two accounts.
  • Virtual threads had the lower p99 in all 6 pairs, but no clear throughput winner: the work is short and CPU-bound, so there is little blocking to hide.
  • An outage cost about 30 % throughput, not a collapse. The breaker opened once; the outbox held ~90,000 postings and drained them all.

Limits of this measurement

  • One run, one 4-core machine: the direction is solid, exact ratios are not.
  • These are lab numbers, never production figures.

Reproduce it on your own machine: ./mvnw -q -pl engine compile exec:java

8 · Limits, and the next step (v3)

The obvious question: "This is all in memory in one JVM. How would it work across many servers?"

Short answer: the engine shows the concurrency rules in-process. Across servers the same rules move into the database: lock rows in id order with SELECT … FOR UPDATE, or use a version column for optimistic updates; enforce idempotency with a unique constraint on the transfer id; write the posting and an outbox row in the same transaction; and let a relay publish outbox rows to the GL. The invariant tests stay the same.

Planned v3: a PostgreSQL ledger (ADR-0002)

Add Why it matters
PostgresLedger (pessimistic: row locks in id order) The standard way to serialise money movement in a relational database.
Optimistic variant (version column, retry) Same pessimistic vs optimistic comparison, now in SQL.
Unique constraint on transfer id Idempotency that survives restarts and works across servers.
Transactional outbox table + relay The standard pattern for "update the database and send a message" without losing either.
Testcontainers in tests The same invariant and stress tests run against a real PostgreSQL.

With this, the project covers both in-memory concurrency and database concurrency. The database tests use Testcontainers, so they need Docker; CI runs them on Ubuntu only.
